# Smart Space Cleaner — Подпроект 1: ядро ревизии (дизайн)

Основа: [исходная спецификация MVP](../../../thoughts/shared/specs/2026-09-16-smart-space-cleaner.md). Этот документ уточняет и местами меняет её для первого подпроекта.

## Цель и контекст

- **Зачем:** учебный проект, который решает личную боль автора. Прототип ставится APK вне Google Play, пользователь пока один — автор.
- **Целевое устройство:** Redmi Note 9 Pro, Android 12 (API 31), MIUI 14, 128 ГБ, на момент проектирования свободно 1,8 ГБ.
- **Учебный приоритет:** чистое разделение слоёв и тесты (TDD) важнее широты функций.
- **Вместо метрики удержания** (она имеет смысл при многих пользователях): реально освобождённое место на телефоне автора и возвращение к уборке через пару недель.

| 2 | Приложения: кэш по каждому приложению и неиспользуемые приложения (`PACKAGE_USAGE_STATS`, уровень 3) | Позже |

Ядро не зависит от LLM: группы и объяснения строятся детерминированно, по правилам.

## Отличия от исходной спецификации

1. **Отмена зависит от уровня риска (вместо «всё в корзину на 7 дней»).** Корзина в той же памяти не освобождает место 7 дней, а при 1,8 ГБ свободного это провал главного обещания. Решение:
   - **Уровень 0** (временные файлы приложения) удаляется сразу. **Кэш приложений** очищает сама система, приложение только отправляет запрос.
   - **Уровень 1, точные дубли** в первой версии тоже уходят в корзину на 7 дней (`DuplicateStrategy.TRASH`). Так автор может своими глазами убедиться, что это действительно дубли. Чтобы место не ждало неделю, в «Истории» есть кнопка «Удалить сейчас» для целой группы. Когда появится уверенность, стратегия переключается одной настройкой на `DELETE_WITH_RESTORE_COPY`: удаление сразу, а отмена копирует оригинал обратно по исходному пути. Обе стратегии реализуются и покрываются тестами уже в подпроекте 1.
   - **Уровень 1, `.apk` установленных приложений** удаляются сразу. Вернуть их нельзя, и интерфейс так и говорит: «скачайте заново».
   - **Уровень 2** (личное) уходит в корзину на 7 дней. Здесь всё по исходной спецификации.
2. **`MANAGE_EXTERNAL_STORAGE` запрашивается сразу.** Публикации в Google Play нет, поэтому модерация не мешает.
3. **Группа «Медиа мессенджеров»** добавлена на уровень 2.
4. **Кэш приложений** перенесён в подпроект 1 в упрощённом виде: одна системная очистка всех приложений сразу.

## Архитектура

Два Gradle-модуля.

### `:core`: чистый Kotlin/JVM, без зависимостей от Android

| Компонент | Ответственность |
|---|---|
| Модель | `FileEntry` (путь, размер, mtime, MIME), `Finding`, `Group`, `RiskLevel` (0–2), `Plan`, `ActionRecord`, `Report` |
| `DuplicateFinder` | Точные дубли: размер → частичный хэш → полный SHA-256 |
| `KeepCopyPolicy` | Выбирает копию, которая останется (правила ниже) |
| `ApkInstallerRule` | `.apk`: установленные приложения → уровень 1, неизвестные → уровень 2 |
| `OldScreenshotRule` | Скриншоты старше порога |
| `LargeFileRule` | Крупные файлы по типам |
| `MessengerMediaRule` | Старые медиа мессенджеров |
| `Planner` | Собирает находки в группы с текстами «что удалится / что останется / почему» и отметками по умолчанию |
| `Executor` | Выполняет только одобренное по стратегии отмены, пишет `ActionRecord` |
| `Restorer` | Отменяет действия из лога |
| `TrashPurger` | Окончательно удаляет записи корзины старше 7 дней |
| Порты | `FileSystem`, `InstalledApps`, `ActionLogStore`, `Clock` |

### `:app`: Android, тонкий слой

- Адаптеры портов: `java.io.File` (через `MANAGE_EXTERNAL_STORAGE`), `PackageManager`, Room (лог и индекс корзины), `StorageStatsManager` (свободное и занятое место).
- `WorkManager`: раз в сутки вызывает `TrashPurger`. Та же проверка выполняется при каждом запуске приложения, на случай если MIUI убьёт фоновую задачу.
- Compose UI (Material 3): экраны «Первый запуск», «Сводка», «План», «Отчёт», «История».
- Зависимости собираются вручную, без DI-фреймворка.

### Поток данных

```
Скан (только чтение) → List<FileEntry> → анализаторы → List<Finding>
  → Planner → Plan (группы) → выбор пользователя → Executor → ActionLogStore
  → Report
```

## Правила сканирования

Значения ниже — **стартовые**. Их уточняем после прогона на реальном телефоне, это отдельная задача плана.

| Параметр | Значение |
|---|---|
| Область | `/storage/emulated/0`, кроме `Android/data`, `Android/obb` и корзины `.SmartSpaceCleaner/` |
| Минимальный размер файла для поиска дублей | 1 КБ |
| Частичный хэш | первые и последние 64 КБ |
| Скриншоты: папки | `DCIM/Screenshots`, `Pictures/Screenshots` |
| Скриншоты: возраст | старше 180 дней |
| Крупные файлы | от 100 МБ, группы: видео, архивы, прочее |
| Мессенджеры: папки | `Android/media/org.telegram.messenger`, `Android/media/com.whatsapp`, `Telegram` |
| Мессенджеры: возраст | старше 90 дней, группа на каждый мессенджер |

Возраст файла считается по `mtime`.

### Какую копию дубликата оставить

Правила применяются по порядку:

1. Сначала сравнивается приоритет папки: `DCIM/Camera` и `Pictures` выше остальных, `Download` и папки мессенджеров ниже всех.
2. Затем имя: имя без суффикса копии (`(1)`, `(0)`, `copy`, `- копия`) важнее имени с суффиксом.
3. Если по-прежнему ничья, остаётся копия с самым коротким путём, а при равной длине — первая по алфавиту, чтобы результат был детерминированным.

### «Рабочие» папки

Группа дублей **по умолчанию не отмечена**, если все её копии лежат вне камеры (`DCIM`, `Pictures`), загрузок (`Download`) и папок мессенджеров.

### Уровни и отметки по умолчанию

| Уровень | Группы | Отмечено по умолчанию | Отмена |
|---|---|---|---|
| 0 | Временные файлы приложения | да | не нужна |
| 0 | Кэш приложений (через систему) | да | невозможна, подтверждает система |
| 1 | Точные дубли | да, кроме «рабочих» папок | корзина на 7 дней (`TRASH`, по умолчанию) или копия оригинала обратно (`DELETE_WITH_RESTORE_COPY`) |
| 1 | `.apk` установленных приложений (версия установленного ≥ версии файла) | да | невозможна |
| 2 | `.apk` неизвестных приложений, старые скриншоты, крупные файлы, медиа мессенджеров | **нет** | корзина на 7 дней |

Группы уровня 2 можно раскрыть, чтобы отметить файлы поштучно.

## Кэш приложений

- Приложение отправляет `StorageManager.ACTION_CLEAR_APP_CACHE` (доступно с API 30, требует `MANAGE_EXTERNAL_STORAGE`). Система показывает свой диалог подтверждения и очищает кэш всех приложений.
- Заранее объём неизвестен, поэтому в карточке написано «объём станет известен после очистки». Фактический результат вычисляется по разнице свободного места до и после.
- **Запасной путь** нужен, если действие недоступно (`resolveActivity` вернул null) или завершилось ошибкой, а такое на MIUI возможно. Тогда приложение показывает кнопку, которая открывает `Settings.ACTION_INTERNAL_STORAGE_SETTINGS`, а в отчёте пишет инструкцию для ручной очистки.

## Экраны

1. **Первый запуск:** зачем нужен полный доступ к файлам и кнопка, ведущая в системную настройку. Без разрешения дальше пройти нельзя, и экран прямо говорит, почему.
2. **Сводка:** свободно и занято, оценка 🔴 (свободно меньше 5%) / 🟡 (5–15%) / 🟢 (больше 15%), 3–4 строки простым языком о главных находках. Пока идёт скан, на экране прогресс и надпись «Пока только смотрю, ничего не удаляю».
3. **План:** группы по уровням 0 → 2. В карточке: название и объём, что удалится, что останется, почему. Группу можно раскрыть и снять отметку с отдельного файла, у изображений есть превью. Кнопка «Выполнить отмеченное (X ГБ)».
4. **Отчёт:** было → стало; сделано по группам; что не сделано и почему, с подсказкой для ручного способа; «освобождено сейчас X ГБ, ещё Y ГБ освободится <дата>»; ссылка на историю.
5. **История:** лог по сессиям. У каждого действия, которое ещё можно отменить, есть кнопка «Вернуть». У элементов в корзине есть кнопка «Удалить сейчас» и для отдельного файла, и для целой группы, например для всех дублей, после того как автор их проверил.

Если группу не отметили, агент её не трогает и в этой сессии больше о ней не спрашивает.

## Исполнение

- **Сначала журнал.** Перед каждым действием создаётся `ActionRecord` со статусом `PENDING`. После успеха он становится `DONE`, при ошибке — `FAILED` с причиной.
- **Восстановление после сбоя.** При запуске приложения каждая запись в статусе `PENDING` сверяется с файловой системой:
  - если файла нет на исходном месте, запись получает `DONE`. Для уровня 2 дополнительно проверяется, что файл лежит в корзине; если его нет и там, запись получает `FAILED` с причиной «файл потерян при сбое», и это показывается в истории;
  - если файл на месте, запись получает `FAILED` с причиной «прервано».
- **Дубль.** Непосредственно перед действием заново считается SHA-256 и удаляемой копии, и оригинала. Если хэши не совпадают или оригинала больше нет, действие получает `FAILED`, а файл не трогается. Если проверка пройдена, дальше всё зависит от стратегии: при `TRASH` копия переносится в корзину, как файлы уровня 2, а при `DELETE_WITH_RESTORE_COPY` удаляется.
- **Уровень 2.** Файл переносится через `rename` в `/storage/emulated/0/.SmartSpaceCleaner/trash/<recordId>`. Исходный путь и срок хранения записываются в лог.
- **Ошибки** (нет доступа, файл занят) не повторяются обходным путём, а уходят в отчёт.
- **После исполнения** изменённые пути передаются в `MediaScannerConnection.scanFile`, чтобы галерея обновилась.

## Отмена (`Restorer`)

- **Дубль при `TRASH`:** так же, как файл из корзины (см. ниже).
- **Дубль при `DELETE_WITH_RESTORE_COPY`:** оригинал копируется обратно по исходному пути. Перед этим проверяется свободное место, после копирования сверяется хэш. Если исходного оригинала уже нет, отмена невозможна, и интерфейс объясняет причину.
- **Корзина:** файл переносится обратно через `rename`. Если путь уже занят, к имени добавляется суффикс ` (восстановлено)`.
- **`.apk` и кэш:** отменить нельзя, в истории написано, как вернуть вручную.

## Тестирование

### `:core`: JUnit 5 на JVM, по TDD

Тесты работают с `FakeFileSystem` в памяти и `FakeClock`. **Тесты безопасности пишутся первыми:**

1. Из группы дублей никогда не удаляется последняя копия.
2. Если содержимое файла изменилось между сканом и исполнением, файл не удаляется.
3. Неотмеченные группы и файлы не затрагиваются.
4. После сбоя посередине исполнения записи `PENDING` корректно сверяются с реальным состоянием.
5. Отмена дубля при любой стратегии даёт файл с тем же хэшем по тому же пути.
6. При `TRASH` дубль не удаляется физически до истечения 7 дней или до явного «Удалить сейчас».
7. `TrashPurger` не удаляет элементы моложе 7 дней.

Плюс модульные тесты на каждое правило анализаторов, `KeepCopyPolicy` и `Planner`.

### `:app`

- Инструментальные тесты на эмуляторе (API 31): DAO Room и адаптер файловой системы на реальных файлах во временной папке.
- Скрипт `adb push` раскладывает на эмуляторе тестовый набор: дубли в разных папках, старые скриншоты (с выставленным `mtime`), `.apk` и крупный файл. На нём проходит ручная проверка.

### Приёмка на телефоне автора

Подпроект 1 готов, когда:

1. Полный скан завершается без сбоев, а время скана выводится на экран.
2. Автор проходит цикл «сводка → план → выполнение → отчёт» и освобождает реальное место. Цифры «было/стало» совпадают с системными настройками с точностью ±100 МБ.
3. Отмена хотя бы одного дубля и одного файла из корзины реально возвращает файл.
4. Очистка кэша сработала либо через системное действие, либо через запасной путь.
5. Пороги скана подтверждены или поправлены по факту.
6. Целевое время полного скана: меньше 3 минут. Это ориентир, а не блокер: если цель не достигнута, фиксируем фактическое время и причину.

## Стек и окружение

- Kotlin 2.x, Jetpack Compose (Material 3), корутины, Room, WorkManager, JUnit 5.
- `minSdk = 31`. `compileSdk` и `targetSdk` берём по последней стабильной версии на момент создания проекта.
- Окружение разработки: Android Studio (JDK, SDK, эмулятор) на Windows. Сейчас ничего из этого не установлено, установка — первая задача плана.
- Порядок проверки: эмулятор API 31 → реальный телефон, на который ставятся только сборки, уже проверенные на эмуляторе.
